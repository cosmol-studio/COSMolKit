# COSMolKit Parity Testing Contract

This document defines the parity testing strategy for COSMolKit.

Parity tests compare COSMolKit behavior against a pinned RDKit version for supported RDKit-compatible features.

Parity tests are not invariant tests.

Invariant tests answer:

> Is the COSMolKit molecule internally self-consistent?

Parity tests answer:

> Does COSMolKit produce the same externally observable behavior as RDKit for this supported feature?

---

## 1. Core Principle

RDKit parity is used as the correctness oracle for supported RDKit-compatible behavior.

A parity test should compare:

```text
same input
same operation
same options
same output schema
COSMolKit output vs RDKit output
```

A parity test should not silently hide mismatches.

If a mismatch is found, the allowed responses are:

```text
fix COSMolKit
verify RDKit behavior from source/docs and update expectation
mark the feature unsupported
register an executable known-failure
```

The disallowed responses are:

```text
relax assertion without explanation
skip the failing field
add molecule-specific hacks
accept multiple outputs without documented reason
move the mismatch into invariant tests
```

---

## 2. Separation from Invariant Tests

Invariant tests and parity tests must remain separate.

### Invariant tests check COSMolKit internal validity

Examples:

```text
bond indices are valid
coordinate rows match atom count
stereo indices do not point to deleted atoms
cache invalidation is correct
source molecule is unchanged after value-style operation
```

### Parity tests check RDKit-compatible behavior

Examples:

```text
SMILES output matches RDKit canonical SMILES
RemoveHs output matches RDKit RemoveHs
Kekulize output matches RDKit Kekulize
Morgan fingerprint bits match RDKit
MolBlock output matches RDKit under a defined normalization
distance bounds match RDKit within tolerance
```

A molecule may pass invariant tests but fail parity.

A molecule may fail invariant tests before parity comparison; in that case, the parity test should report:

```text
COSMolKit invalid output before parity comparison
```

but the invariant failure itself should belong to the invariant test suite.

---

## 3. Pinned Reference Policy

Parity must always target a pinned RDKit version.

The pinned RDKit version should be recorded in one or more of:

```text
testdata/README.md
generated expected-data manifest
generator script version assertion
CI environment lockfile
```

A parity test must not depend on an unspecified local RDKit version.

If RDKit is upgraded, golden files must be regenerated intentionally and reviewed.

---

## 4. Parity Test Categories

COSMolKit parity tests should be grouped by feature domain.

Recommended layout:

```text
crates/<owning-crate>/tests/
  smiles/
    read_parity.rs
    write_parity.rs
    canonical_smiles_parity.rs

  sdf/
    sdf_read_parity.rs
    sdf_write_parity.rs
    molblock_read_parity.rs
    molblock_write_parity.rs

  hydrogens/
    add_hs_parity.rs
    remove_hs_parity.rs

  kekulize/
    kekulize_parity.rs

  sanitize/
    sanitize_parity.rs

  stereo/
    stereo_assignment_parity.rs
    isomeric_smiles_parity.rs

  fingerprint/
    morgan_fingerprint_parity.rs

  distgeom/
    bounds_matrix_parity.rs

  depiction/
    drawing_prepare_parity.rs
    svg_output_parity.rs
```

If the current test layout is flatter, this domain structure can still be used conceptually.

---

## 5. Parity Input Corpus

Parity tests should use explicit, version-controlled corpora.

Recommended layout:

```text
testdata/<domain>/corpus/
  smiles_core.csv
  smiles_aromatic.csv
  smiles_charged.csv
  smiles_stereo.csv
  smiles_hydrogen_sensitive.csv
  sdf_v2000_cases.sdf
  sdf_v3000_cases.sdf
  molblock_edge_cases.jsonl
```

For CSV corpora, recommended fields are:

```text
case_id
input
input_type
tags
description
source
notes
```

Example:

```csv
case_id,input,input_type,tags,description
smiles_basic_001,CCO,smiles,basic|organic,ethanol
smiles_arom_001,c1ccccc1,smiles,aromatic|kekulize,benzene
smiles_stereo_001,F[C@](Cl)(Br)I,smiles,stereo|tetrahedral,tetrahedral stereocenter
```

The corpus should include both:

```text
small curated cases
large stress-test samples
```

Curated cases should run in normal CI.

Large stress tests may run in scheduled CI or manual validation.

---

## 6. Golden Generation Policy

Parity expected outputs should be generated by deterministic RDKit generator scripts.

Recommended layout:

```text
testdata/<domain>/expected/rdkit/<profile>/
  manifest.json
  <expected-output>.jsonl

tools/testdata/rdkit/
  generate_all.py
  _generate_<feature>.py
```

The public preparation entrypoint should:

```text
assert RDKit version
read version-controlled corpus
write deterministic JSONL
record feature name
record options
record output schema version
validate exact cache identity and output checksums before reuse
publish generated domain directories atomically
```

Generated expected outputs are uncommitted and may be cached locally or in
CI. Restoring a cache never bypasses preparation-time identity validation.
Ordinary test binaries validate only the manifest entry and output they
consume; they do not regenerate data or rescan unrelated outputs.

A golden row should usually include:

```json
{
  "case_id": "smiles_basic_001",
  "input": "CCO",
  "feature": "canonical_smiles",
  "options": {
    "isomeric": true,
    "kekule": false
  },
  "rdkit_output": "CCO",
  "status": "ok"
}
```

If RDKit itself fails on an input, the row should record that explicitly:

```json
{
  "case_id": "bad_case_001",
  "feature": "sanitize",
  "status": "rdkit_error",
  "rdkit_error_kind": "AtomValenceException",
  "rdkit_error_message": "..."
}
```

COSMolKit should then compare against RDKit error behavior when that behavior is part of the supported contract.

---

## 7. Output Schema Policy

Every parity test must define exactly what is compared.

Do not compare vague or incidental outputs.

For each parity feature, define an output schema.

### Example: canonical SMILES parity

Compare:

```text
canonical_smiles
isomeric flag
kekule flag if applicable
```

Do not compare:

```text
internal atom ordering unless explicitly part of the test
debug logs
incidental formatting
```

### Example: RemoveHs parity

Compare one or more of:

```text
canonical isomeric SMILES after RemoveHs
atom count
bond count
explicit H counts
formal charges
isotopes
atom map numbers
stereo tags
MolBlock output if relevant
```

The test should specify whether the primary oracle is:

```text
canonical SMILES
structured molecule state dump
MolBlock
fingerprint
```

### Example: bounds matrix parity

Compare:

```text
matrix shape
lower/upper bounds
numeric tolerance
failure status
```

with explicit tolerance:

```text
absolute_tolerance = 1e-6
relative_tolerance = 1e-6
```

---

## 8. Normalization Policy

Some RDKit outputs are not stable under raw string comparison.

Parity tests may apply explicit normalization before comparison.

Allowed normalization examples:

```text
line ending normalization
trailing whitespace trimming
floating-point formatting normalization
SDF property ordering normalization if RDKit order is not the target
SVG metadata stripping if metadata is not chemically meaningful
```

Forbidden normalization examples:

```text
removing fields only because they mismatch
sorting atoms unless atom order is not part of the expected behavior
dropping stereo annotations without declaring stereo unsupported
ignoring charges/aromaticity/bond types
```

Any normalization must be documented next to the test.

---

## 9. Parity Test Execution Flow

A parity test should follow this flow:

```text
1. Load corpus case.
2. Load corresponding RDKit golden output.
3. Run COSMolKit operation with the same options.
4. If COSMolKit returns error:
     compare with RDKit error expectation.
5. If COSMolKit returns molecule:
     optionally run basic invariant sanity check.
6. Extract COSMolKit output according to parity output schema.
7. Normalize COSMolKit and RDKit outputs if required.
8. Compare.
9. If mismatch:
     check known-failure registry.
10. Report pass, expected failure, unexpected pass, or unexpected failure.
```

Important:

> Step 5 should not turn the parity suite into the invariant suite. It should only prevent comparing obviously invalid COSMolKit output.

---

## 10. Known-Failure Policy

Known failures must be executable expected failures, not skipped tests.

Known failure records should have common fields plus domain-specific fields.

### Common fields

```text
case_id
failure_domain
feature
expected_failure_kind
reason
created_at
```

### RDKit parity-specific fields

```text
rdkit_version
input_type
options
expected_mismatch_field
tracking_issue
```

Example:

```json
{
  "case_id": "molblock_1065",
  "failure_domain": "rdkit_parity",
  "feature": "molblock_write",
  "expected_failure_kind": "MolBlockMismatch",
  "expected_mismatch_field": "bond_block",
  "reason": "Known mismatch under kekulize=false behavior",
  "rdkit_version": "2026.03.1",
  "created_at": "2026-05-08"
}
```

A known failure must:

```text
still execute
match the expected failure kind
fail the test if it unexpectedly passes
fail the test if it fails in a different way
```

Known failures must not be silent skips.

---

## 11. Error Parity Policy

Some parity tests compare errors, not successful outputs.

If RDKit errors and COSMolKit errors, the comparison should check:

```text
same error category if supported
same failure stage if known
enough context to confirm equivalent behavior
```

Exact error message parity is usually not required unless explicitly specified.

Recommended error categories:

```text
ParseError
SanitizeError
ValenceError
KekulizeError
StereoError
UnsupportedFeature
InvalidMoleculeState
```

If RDKit accepts an input but COSMolKit errors, then either:

```text
COSMolKit is incomplete
feature should be marked unsupported
known failure should be registered
```

If RDKit errors but COSMolKit accepts, then either:

```text
COSMolKit is more permissive intentionally
behavior must be documented
or it is a bug
```

---

## 12. Option Parity Policy

RDKit operations often have options.

Parity tests must record the exact options used.

Examples:

```text
RemoveHsParameters
sanitize = true / false
kekulize = true / false
canonical = true / false
isomericSmiles = true / false
includeChirality = true / false
useBondTypes = true / false
```

COSMolKit should not claim parity for an operation without specifying the option profile.

Recommended profile naming:

```text
remove_hs_default_rdkit
remove_hs_track_isotopes
remove_hs_keep_mapped
smiles_canonical_isomeric
smiles_kekule_nonisomeric
morgan_radius2_chiral
```

A parity test case should include:

```json
{
  "feature": "remove_hs",
  "profile": "remove_hs_default_rdkit",
  "options": {
    "sanitize": true,
    "removeIsotopes": false,
    "removeMapped": false
  }
}
```

## 13. Structured Molecule State Dump

For complex parity features, canonical SMILES alone is not enough.

COSMolKit and RDKit should both be able to dump a structured molecule state.

Recommended dump schema:

```json
{
  "atoms": [
    {
      "idx": 0,
      "atomic_num": 6,
      "formal_charge": 0,
      "isotope": 0,
      "is_aromatic": false,
      "explicit_h_count": 0,
      "implicit_h_count": 3,
      "chiral_tag": "CHI_UNSPECIFIED",
      "atom_map_num": 0
    }
  ],
  "bonds": [
    {
      "idx": 0,
      "begin": 0,
      "end": 1,
      "bond_type": "SINGLE",
      "is_aromatic": false,
      "stereo": "STEREONONE"
    }
  ],
  "props": {},
  "conformers": {
    "count": 0
  }
}
```

Use structured state dump parity for:

```text
hydrogen transforms
sanitize
kekulize
stereo
MolBlock read/write
```

Canonical SMILES may remain the primary comparison for simpler cases.

## 14. Feature-Specific Parity Profiles

### SMILES write parity

Inputs:

```text
SMILES corpus
SDF corpus optionally converted to molecule
```

Compare:

```text
canonical SMILES
isomeric SMILES
kekule SMILES if supported
```

Golden output:

```json
{
  "case_id": "...",
  "feature": "smiles_write",
  "profile": "canonical_isomeric",
  "rdkit_output": "..."
}
```

---

### SMILES read parity

Compare:

```text
parse success/error
structured atom/bond state
canonical isomeric SMILES after parse
```

Do not require identical internal atom order unless the parser contract specifies it.

---

### RemoveHs parity

Compare:

```text
success/error
atom count
bond count
canonical isomeric SMILES
structured atom/bond state
stereo state
tracked isotope behavior if option enabled
```

Must record exact `RemoveHsParameters`.

---

### AddHs parity

Compare:

```text
success/error
atom count
bond count
explicit H placement in graph
coordinates if addCoords is supported
canonical isomeric SMILES if stable
structured state dump
```

Must record exact `AddHsParameters`.

---

### Kekulize parity

Compare:

```text
success/error
bond types
aromatic flags
canonical kekule SMILES if stable
structured bond state
```

Must distinguish:

```text
clearAromaticFlags = true
clearAromaticFlags = false
```

if supported.

---

### Sanitize parity

Sanitize is a pipeline, so parity should be profile-based.

Compare:

```text
success/error
final canonical SMILES
formal charges
implicit H counts
aromatic flags
bond types
stereo if affected
```

Must record sanitize flags.

---

### Stereo parity

Compare:

```text
isomeric SMILES
atom chiral tags
bond stereo
wedge/dash-derived stereo if applicable
CIP rank/label only if explicitly supported
```

CIP labels may require special handling and should not be compared unless COSMolKit explicitly supports them.

---

### Morgan fingerprint parity

Compare:

```text
bit vector or sparse counts
radius
nBits
useChirality
useBondTypes
useFeatures
```

Fingerprint parity should use exact option profiles.

---

### Distance bounds parity

Compare:

```text
bounds matrix shape
lower/upper bounds
numeric tolerance
failure behavior
```

Must record:

```text
useMacrocycle14config
set15bounds
scaleVDW
other relevant options
```

if exposed.

---

### MolBlock / SDF parity

Compare:

```text
read success/error
write success/error
atom block
bond block
charge/isotope/stereo fields
coordinate block
SDF properties
```

Raw string parity is allowed only after documented normalization.

Structured MolBlock parsing comparison is preferred when raw formatting is not the target.

---

## 15. Parity Result Types

Each parity case should classify result as one of:

```text
pass
expected_failure
unexpected_failure
unexpected_pass
unsupported
rdkit_error_matched
rdkit_error_mismatch
```

Suggested Rust enum:

```rust
pub enum ParityCaseResult {
    Pass,
    ExpectedFailure,
    UnexpectedFailure,
    UnexpectedPass,
    Unsupported,
    RdkitErrorMatched,
    RdkitErrorMismatch,
}
```

This makes CI output easier to understand.

## 16. CI Policy

Recommended CI tiers:

### Tier 1: Fast required parity

Runs on every PR.

```text
small curated corpus
core SMILES
core hydrogen transforms
core kekulize
core SDF/MolBlock smoke tests
core fingerprint cases
```

### Tier 2: Extended parity

Runs manually or scheduled.

```text
large corpus
stress SDF/MolBlock cases
core_comp_lib samples
rare stereo cases
large fingerprint parity
depiction regression
```

### Tier 3: RDKit upgrade validation

Runs only when RDKit version changes.

```text
regenerate all golden files
compare golden diffs
review changed behavior
update pinned version metadata
```

## 18. Mismatch Report Format

A parity mismatch should report enough context to reproduce.

Required mismatch report fields:

```text
case_id
feature
profile
input
options
rdkit_version
expected output
actual output
mismatch field
known-failure status
```

For structured output, report a focused diff.

Example:

```text
case_id: smiles_stereo_001
feature: remove_hs
profile: remove_hs_default_rdkit
mismatch_field: atoms[3].chiral_tag

RDKit:
  CHI_TETRAHEDRAL_CCW

COSMolKit:
  CHI_UNSPECIFIED
```

## 19. Relationship to Operation Registry

The operation registry is the source of truth for parity obligations.

Registry entries must use `ParityPolicy`, not a boolean `rdkit_parity` flag.

```text
ParityPolicy::NotApplicable
ParityPolicy::RequiredWhenSupported
ParityPolicy::RequiredNow
```

The meanings are:

```text
NotApplicable
  RDKit is not the behavior oracle for this operation.

RequiredWhenSupported
  The operation is intended to match RDKit once its SupportStatus is no longer
  Unsupported. The operation may already appear in PARITY_MATRIX so tests can
  assert explicit unsupported behavior until implementation lands.

RequiredNow
  The operation currently claims RDKit-compatible supported behavior. It must
  appear in PARITY_MATRIX and must have a parity profile, corpus, golden output,
  comparison schema, and known-failure handling if needed.
```

Example:

```rust
op without_hydrogens {
    kind: Strong,
    may_mutate: [Topology, Conformers],
    must_handle: [Coordinates, Stereo, Caches],
    support: Unsupported,
    parity: RequiredWhenSupported,
}
```

This implies:

```text
the operation should appear in PARITY_MATRIX with a RemoveHs profile
while unsupported, tests should assert explicit UnsupportedFeature behavior
once supported, there must be corpus coverage for this operation
once supported, there must be golden output generated from RDKit
once supported, known failures must be executable xfails
```

For `RequiredNow`, all of the "once supported" requirements apply immediately.

The generated `PARITY_MATRIX` connects:

```text
operation spec
feature spec
parity profile name
pinned RDKit version or a required lookup to pinned test metadata
```

Parity tests should be generated or selected from `PARITY_MATRIX`; they should
not use hand-maintained operation lists.

---

## 20. What Parity Tests Should Not Do

Parity tests should not:

```text
test every internal invariant directly
replace invariant tests
hide mismatches by normalization
skip known mismatches silently
compare unstable formatting without normalization
mix multiple unrelated features in one assertion
depend on unpinned RDKit behavior
use broad catch-all expected outputs
```

Parity tests should stay focused:

> Compare COSMolKit externally observable behavior to RDKit for one feature profile.

---

## 21. Summary

Parity testing in COSMolKit should follow this model:

```text
Invariant tests:
  Is COSMolKit internally consistent?

Parity tests:
  Does COSMolKit match RDKit for supported behavior?

Golden files:
  Deterministic RDKit-generated expected outputs.

Known failures:
  Executable expected failures, never skipped silently.

Operation registry:
  Declares which operations require parity.

Output schemas:
  Define exactly what fields are compared.

Option profiles:
  Define exactly which RDKit/COSMolKit settings are being matched.
```

The shortest rule:

> Parity tests compare behavior, not implementation.  
> Invariant tests protect internal state.  
> Both are required, but they must not be mixed.

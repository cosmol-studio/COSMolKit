### RDKit Source Behavior

- `third_party/rdkit/Code/GraphMol/Descriptors/Lipinski.cpp::ss_matcher` constructs a query molecule with `RDKit::SmartsToMol(pattern)`.
- `ss_matcher::countMatches` calls `RDKit::SubstructMatch(mol, nm, matches)` with default `SubstructMatchParameters`, then returns `matches.size()`.
- Default RDKit substructure parameters in `SubstructMatch.h` include `recursionPossible = true`, `uniquify = true`, and `maxMatches = 1000`.
- `SMARTSCOUNTFUNC(NumHBD, ...)` uses:
  - `[N&!H0&v3,N&!H0&+1&v4,O&H1&+0,S&H1&+0,n&H1&+0]`
- `SMARTSCOUNTFUNC(NumHBA, ...)` uses:
  - `[$([O,S;H1;v2]-[!$(*=[O,N,P,S])]),$([O,S;H0;v2]),$([O,S;-]),$([N;v3;!$(N-*=!@[O,N,P,S])]),$([nH0X2,o,s;+0])]`

### Current COSMolKit Support

- `crates/cosmolkit-core/src/search/smarts_parse.rs::parse_smarts` parses the atom predicates required by HBD:
  - aliphatic `N`, `O`, `S`
  - aromatic `n`
  - logical `&`, `,`, and `!`
  - `H0`/`H1` as `AtomQueryPredicate::HydrogenCount`
  - `v3`/`v4` as `AtomQueryPredicate::TotalValence`
  - `+0`/`+1` as `AtomQueryPredicate::FormalCharge`
- `crates/cosmolkit-core/src/search/query.rs` evaluates those HBD predicates against molecule atoms using:
  - `HydrogenCount` through `getTotalNumHs(true)`-equivalent logic
  - `TotalValence` through RDKit-like valence assignment
  - `FormalCharge`, `AtomType`, and aromaticity directly from atom state
- `crates/cosmolkit-core/src/chemistry/forcefield/crystalff/torsion_preferences.rs::build_crystalff_query_molecule` can convert parsed SMARTS query trees into a `Molecule` query used by `get_substruct_matches`.
- `crates/cosmolkit-core/src/search/substruct.rs::get_substruct_matches` defaults to `max_matches = 1000` and `uniquify = true`, matching RDKit's default count surface for `SMARTSCOUNTFUNC`.

### Gaps And Blockers

- HBD does not contain recursive SMARTS. Its required predicate set is present in the current parser/evaluator, so Step 25 may port `calc_num_hbd` through the same `SmartsToMol` + `SubstructMatch` shape, provided the RDKit source lines are copied into the Rust function/helper and the parity test confirms `num_hbd` disappears from the failure summary.
- HBA depends on recursive SMARTS `$()` and nested negated recursive SMARTS such as `!$(*=[O,N,P,S])` and `!$(N-*=!@[O,N,P,S])`.
- `substruct.rs` has a recursive SMARTS cache path, but the relevant functions are still marked with `RDKit❗✔️` in source comments, including recursive query matching and atom compatibility paths. Under `dev/source_reproduction_protocol.md`, that is not enough to claim full source reproduction for HBA.
- Therefore Step 29 must not silently port HBA by relying on current recursive SMARTS behavior unless that recursive SMARTS path is first audited/upgraded to source-backed status for the exact HBA input state space, or unless `calc_num_hba` implements the exact source-required SMARTS behavior in a private, source-anchored helper.

### Step 23 Conclusion

- `calc_num_hbd` is actionable next without adding heuristic chemistry rules.
- `calc_num_hba` remains blocked on a narrower recursive-SMARTS/source-reproduction proof before it can be marked complete.

### RDKit Source Behavior

- `third_party/rdkit/Code/GraphMol/Descriptors/Lipinski.cpp::SMARTSCOUNTFUNC(NumHBA, ...)` uses:
  - `[$([O,S;H1;v2]-[!$(*=[O,N,P,S])]),$([O,S;H0;v2]),$([O,S;-]),$([N;v3;!$(N-*=!@[O,N,P,S])]),$([nH0X2,o,s;+0])]`
- The descriptor path is still `ss_matcher`:
  - `SmartsToMol(pattern)`
  - `SubstructMatch(mol, query, matches)` with default `SubstructMatchParameters`
  - `matches.size()`
- Required recursive SMARTS fragments for this pattern:
  - `$([O,S;H1;v2]-[!$(*=[O,N,P,S])])`
  - `$(*=[O,N,P,S])`
  - `$([N;v3;!$(N-*=!@[O,N,P,S])])`
  - `$(N-*=!@[O,N,P,S])`
  - `$([nH0X2,o,s;+0])`

### Current COSMolKit Support

- `crates/cosmolkit-core/src/search/smarts_parse.rs` parses the atom-level primitives used by the HBA pattern:
  - `O`, `S`, `N`, aromatic `n`, `o`, `s`
  - `H0`, `H1`, `v2`, `v3`, `X2`, `+0`, `-`
  - atom OR through comma and low-precedence AND through semicolon
  - recursive SMARTS `$()`
- `crates/cosmolkit-core/src/chemistry/forcefield/crystalff/torsion_preferences.rs::build_crystalff_query_molecule` can convert parsed HBA-like SMARTS trees into query molecules with atom query trees and bond query trees.
- `crates/cosmolkit-core/src/search/substruct.rs` has a recursive SMARTS cache path that records whether each molecule atom can be the root of an inner recursive query and then evaluates `AtomQueryPredicate::RecursiveSmarts` through that cache.

### Source-Reproduction Gaps

- The relevant recursive SMARTS matching functions in `substruct.rs` are still marked `RDKit❗✔️`, including:
  - `recursive_smarts_root_matches`
  - atom query evaluation through the recursive cache
  - bond compatibility and general atom compatibility comments around the query path
- `query.rs::atom_predicate_matches_with_context` still returns `false` for `AtomQueryPredicate::RecursiveSmarts` outside the substructure-specific recursive-cache path. That is acceptable only when every HBA evaluation reaches the substructure path; it is not a source-backed proof of general recursive SMARTS behavior.
- The HBA branch `$([O,S;H1;v2]-[!$(*=[O,N,P,S])])` depends on a negated recursive SMARTS predicate on the neighbor atom. Current code can represent `Not(RecursiveSmarts(...))`, but the source markers do not yet prove RDKit-equivalent root anchoring and negation semantics for this descriptor input space.
- The HBA branch `$(N-*=!@[O,N,P,S])` depends on a mixed bond expression where `=` and `!@` are both constraints on the same bond. Current parser/build code appears capable of representing it, but the source anchors for that exact bond-query composition remain generic and not descriptor-specific.

### Step 29 Conclusion

- Step 29B must not port `calc_num_hba` by simply invoking the current recursive SMARTS path while that path remains `RDKit❗✔️`.
- Before Step 29B can be completed, the implementation must either:
  - source-upgrade the exact recursive SMARTS and bond-query behavior required by the HBA pattern to `RDKit✔️` status with copied RDKit source anchors and focused tests, or
  - implement a private, descriptor-local matcher whose behavior is directly anchored to RDKit SMARTS/substructure source lines for the HBA input state space.
- Hand-coded acceptor chemistry predicates are not acceptable for Step 29B because the RDKit source behavior is SMARTS parsing plus substructure matching, not a separate procedural acceptor algorithm.

- Plan step: `dev/rdkit_molecular_descriptors_full_port_plan.md` Step 49.
- Required rules freshly loaded before this audit:
  - `dev/policy_invariants.md`
  - `dev/source_reproduction_protocol.md`

### RDKit Source Behavior

- `third_party/rdkit/Code/GraphMol/Descriptors/Crippen.cpp::CrippenParamCollection::CrippenParamCollection` selects `defaultParamData` when `paramData == ""`, reads rows with tab separation and `boost::keep_empty_tokens`, skips rows whose first character is `#`, and assigns increasing `idx` values in source row order.
- Each non-comment row is parsed as:
  - label
  - SMARTS
  - logP, with empty field mapped to `0.0`
  - MR, with empty field or failed lexical cast mapped to `0.0`
  - compiled SMARTS via `SmartsToMol(paramObj.smarts)`
- `getCrippenAtomContribs` iterates the parameter records in order. For each record it calls `SubstructMatch(mol, *(param.dp_pattern.get()), matches, false, true)`, i.e. `uniquify=false` and recursive matching enabled.
- For each match, RDKit reads `(*matchIt)[0].second`; only the first query atom's target atom is typed. If that target atom is still needed, RDKit assigns the parameter logP/MR and marks the atom as no longer needed. First parameter match wins per atom.
- `calcCrippenDescriptors` optionally calls `MolOps::addHs(mol, false, false)`, computes atom contributions on the working molecule, and sums logP contributions first, then MR contributions.

### Current COSMolKit Support

- The Crippen `defaultParamData` SMARTS table uses no recursive SMARTS `$()`.
- The table does require SMARTS parsing/substructure support for:
  - bracket atoms with atomic-number lists, element symbols, aromatic `a`/`c`/`n`/`o`/`s`, aliphatic `A`, wildcard `*`, `!`, comma OR, `;` low-precedence AND, and implicit adjacent AND
  - hydrogen count primitives such as `H`, `H0`, `H1`, `H2`, `H3`, `H4`
  - degree/connectivity primitives such as `X1`, `X2`, `X4`
  - ring/aromatic predicates such as `a`, `A`, and `cH0`
  - formal charges including `+`, `+0`, `+2`, `+3`, `-`, `-0`, `-2`, `-3`, `-4`, `+5`, `+6`
  - bond primitives `-`, `=`, `#`, `:` and branch structure
- `crates/cosmolkit-core/src/search/smarts_parse.rs` currently has parser support for those primitives and for the bond-expression precedence needed by mixed bond expressions.
- `crates/cosmolkit-core/src/search/query.rs` has evaluator support for the required non-recursive atom and bond predicates, but some comments around the generic substructure atom-compatibility path still carry partial-source markers. Crippen implementation must therefore validate the exact parameter table through parity, not infer full generic SMARTS completeness.
- `crates/cosmolkit-core/src/search/substruct.rs::get_substruct_matches_with_params` exposes `SubstructMatchParams { uniquify, max_matches }`, so Crippen can call with `uniquify=false` to match RDKit's `SubstructMatch(..., false, true)` call shape.

### Gaps And Required Implementation Constraints

- The existing descriptor helper `rdkit_count_query_matches` is not suitable for Crippen because it uses default `uniquify=true` and returns only a count. Crippen needs the complete ordered match list with `uniquify=false` and must inspect `match.atom_mapping[0]`.
- The Rust port must preserve parameter row order exactly. Reordering rows by label or SMARTS would change first-match atom typing.
- Empty MR/logP fields must be represented as `0.0` exactly as the RDKit constructor does. Rows such as `N10`, `N12`, `Hal`, and transition-metal rows intentionally have blank MR fields.
- The source table contains split C++ string literals for a few long rows. The Rust source table must preserve the concatenated row contents, not the visual C++ line wrapping.
- `includeHs=true` cannot be approximated by implicit-hydrogen arithmetic inside Crippen. RDKit computes contributions after `MolOps::addHs(mol, false, false)`, so the Rust implementation must either call the source-backed explicit-hydrogen operation or keep Crippen unsupported for `include_hs=true`.

### Step 49 Conclusion

- Step 51 may port the parameter-table helper directly from `defaultParamData` and `CrippenParamCollection::CrippenParamCollection`.
- Step 53 must use `get_substruct_matches_with_params` with `uniquify=false`, assign only `atom_mapping[0]`, and preserve the source first-match semantics.
- Step 55 must not implement Crippen by summing per-element or hand-written atom-type heuristics; the source behavior is ordered SMARTS matching plus optional explicit hydrogen expansion.

### RDKit Source Behavior

- `third_party/rdkit/rdkit/Chem/QED.py` defines:
  - `QEDproperties = namedtuple('QEDproperties', 'MW,ALOGP,HBA,HBD,PSA,ROTB,AROM,ALERTS')`
  - `ADSparameter = namedtuple('ADSparameter', 'A,B,C,D,E,F,DMAX')`
  - `WEIGHT_MEAN = QEDproperties(0.66, 0.46, 0.05, 0.61, 0.06, 0.65, 0.48, 0.95)`
  - two alternate weight sets, `WEIGHT_MAX` and `WEIGHT_NONE`, which are not used by the current COSMolKit `calc_qed` surface.
- `ads(x, adsParameter)` computes:
  - `exp1 = 1 + math.exp(-1 * (x - p.C + p.D / 2) / p.E)`
  - `exp2 = 1 + math.exp(-1 * (x - p.C - p.D / 2) / p.F)`
  - `dx = p.A + p.B / exp1 * (1 - 1 / exp2)`
  - `dx / p.DMAX`
- `properties(mol)`:
  - rejects `None`, then calls `Chem.RemoveHs(mol)`.
  - computes `MW` with `rdmd._CalcMolWt(mol)`.
  - computes `ALOGP` with `Crippen.MolLogP(mol)`.
  - computes QED-specific `HBA` as the sum of `len(mol.GetSubstructMatches(pattern))` for each SMARTS in `AcceptorSmarts`, gated by `mol.HasSubstructMatch(pattern)`.
  - computes `HBD` with `rdmd.CalcNumHBD(mol)`.
  - computes `PSA` with `MolSurf.TPSA(mol)`.
  - computes `ROTB` with `CalcNumRotatableBonds(..., Strict)`.
  - computes `AROM` as `len(Chem.GetSSSR(Chem.DeleteSubstructs(Chem.Mol(mol), AliphaticRings)))`, explicitly noting this is not equivalent to `Lipinski.NumAromaticRings`.
  - computes `ALERTS` as the number of structural-alert SMARTS patterns with at least one substructure match.
- `qed(mol, w=WEIGHT_MEAN, qedProperties=None)` computes properties when absent, maps each property through `ads`, then returns `math.exp(sum(wi * math.log(di) for wi, di in zip(w, d)) / sum(w))`.

### Already Covered Dependencies

- `MW`: `calc_mol_wt(mol, false)` is source-backed from RDKit `calcAMW` / `getAvgMolWt`.
- `ALOGP`: `calc_crippen_descriptors(mol, true, false).logp` is source-backed from RDKit `calcCrippenDescriptors` with `includeHs=true`, matching `Crippen.MolLogP`.
- `HBD`: `calc_num_hbd` is source-backed through RDKit `SMARTSCOUNTFUNC(NumHBD, ...)`.
- `PSA`: `calc_tpsa(mol, false, false)` is source-backed from RDKit `calcTPSA` / `getTPSAAtomContribs`.
- `ROTB`: `calc_num_rotatable_bonds(mol, Strict)` is source-backed from RDKit `calcNumRotatableBonds` strict branch.

### QED-Specific Gaps

- QED `HBA` must not reuse `calc_num_hba`. RDKit QED uses its own `AcceptorSmarts` list and sums all match counts across the list.
- `AcceptorSmarts` includes 11 SMARTS patterns. The current SMARTS/substructure path appears to cover their primitives, but implementation must compile each source pattern and count matches through RDKit-style substructure matching rather than replacing them with hand-written acceptor predicates.
- `ALERTS` requires compiling and testing every SMARTS string in `StructuralAlertSmarts`. The list is large and includes advanced patterns such as isotope queries (`[15N]`, `[13C]`, `[18O]`, `[34S]`), recursive SMARTS, ring-count/ring-membership predicates (`R`, `R0`, `R1`, `R2`), atom/bond negation, `@` ring bonds, `!@`, disconnected SMARTS with `.`, and long fused-aromatic patterns. Any unsupported parser or matcher primitive must return structured unsupported rather than silently lowering the alert count.
- `AROM` depends on `Chem.DeleteSubstructs(Chem.Mol(mol), AliphaticRings)` followed by `Chem.GetSSSR`. There is no existing source-backed delete-substructure operation in `descriptors.rs`; this must be ported for the QED input state space, or QED must remain unsupported. Reusing `calc_num_aromatic_rings` would violate the RDKit source comment because RDKit explicitly says the replacement is not identical.
- `Chem.RemoveHs(mol)` at the start of `properties` means QED must either call the existing source-backed hydrogen-removal operation with RDKit-compatible default sanitization for the modeled inputs or fail closed when hydrogen removal is unsupported.

### Required Implementation Constraints

- Step 67 can port only `ads` and constants/tables. It must include the ADS parameters, mean weights, acceptor SMARTS, aliphatic-ring SMARTS, and structural-alert SMARTS as source-order data. It is not a completed QED implementation by itself.
- Step 69 must implement `properties` without heuristic substitutions:
  - use QED-specific acceptor SMARTS for HBA,
  - use `DeleteSubstructs`-then-`GetSSSR` semantics for `AROM`,
  - use structural-alert `HasSubstructMatch` semantics for `ALERTS`,
  - preserve the source property order used by `qedProperties._asdict().items()`.
- Step 71 must reproduce the Python numeric expression order in `qed`, including `math.log` before weighted sum and `math.exp(t / sum(w))`.
